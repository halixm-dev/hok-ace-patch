# 10: Continue Android checkpoints without discarding completed work

Status: ready-for-agent
Implementation: complete
Verification: pending
Blocked by: 08, 09

## Scope and files

Own `PatchCoordinator.kt`, continuation portions of `SessionJournal.kt`, `AutomaticRoute.kt` and dispatch integration in `MainActivity.kt/PatchWorkerService.kt`. Read architecture sections 3–5/7 and existing recovery probe scenarios. Preserve root and normal/access paths.

## Steps

1. Add deterministic startup/reconnect dispatch: attach to a matching live worker, otherwise claim durable intent under the shared lock. No new auto work from status or a clean idle screen.
2. Refactor coordinator entry into checkpoint operations. Reuse prepared/snapshot/STAGED work through ticket 09 APIs; incomplete snapshot/build restarts only that stage.
3. Preserve recovery: rollback incomplete apply from verified originals, then reuse valid staged output; forward-complete verified payload awaiting normal restoration. Reconcile file/install outcomes committed before lost replies.
4. Separate “consistency recovered” from “action cancelled.” Unexpected interruption keeps continuation authorized; explicit Stop revokes it. Keep payload/APK/finalization result distinct and publish complete only after all gates.
5. Change releaseIfResolved/releaseSession/startup cleanup to pin continuation and recovery references. Preserve stopped reusable work; prune only eligible unreferenced resolved data.
6. Invalidate by actual inputs. Preserve recovered_unconfirmed history, correct delta knowledge and existing package safety; start a fresh validation/snapshot/build when safe. Promoting pristine knowledge from an unconfirmed old payload is not a success receipt. Recovery must work without Python/updated codecs when only saved bytes/APK are needed.
7. Make final delta promotion/removal and final receipt idempotent; a kill after normal restoration but before promotion must recover safely without rebuilding.

## Acceptance

- [ ] Snapshot/build call counters prove complete-stage reuse and incomplete-stage-only restart.
- [ ] Repeated apply/rollback interruption retains the full expected layer and old/pending pristine knowledge.
- [ ] Final-install-only recovery does no translation build/write; lost install reply audits actual installed identity.
- [ ] Legacy phases recover safely; no unauthorized continuation is invented.
- [ ] Root performs zero APK installs and preserves ownership/labels; exact provider remains bound.
- [ ] Unconfirmed results never become complete/receipt-eligible without a fresh verified run.

### Known concerns

- On a fresh launch, a confirmed continuable action is continued automatically. This is my reading of step 1 ("claim durable intent"). It needs a product check, because the old comment said opening the app never starts game changes.
- Recovery through the `recover` action re-audits a verified payload by installing the access APK, then installs the normal APK again. Only `dispatch` takes the no-install finalization-only path.
- `checkpoint_identity` gets `RunStore.Run.preparation` (the binding record) as its prepared-APK evidence. This may need the full identities if ticket 09 meant them.
- Retention keeps one resolved linked session, the newest. Free up space still releases older ones, including their `finalization/previous-*` backups.
- The FullCoordinator continuation probe assumes `inspect_build_checkpoint` succeeds with a real engine and producer identity. If the producer is null, reuse is skipped and the probe fails by design.
- `resumeConsistent` resets the phase to PREPARED and keeps the snapshot and build records. Reuse is decided only by revalidation.
