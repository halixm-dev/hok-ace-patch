# HOK ACE Mobile English Patcher

Windows app that installs the English or Indonesian translation into 王者万象棋
(`com.tencent.tmgp.osgame`) on an Android phone over USB, without root. Pick the language under
**LANGUAGE** in the app before starting; the choice is remembered. The translation is written into the game data
**after** the in-game update finishes, because Tencent's updater applies binary diffs that break
if the language packages were modified inside the APK.

## Build

Requires Python **3.12** (the runtime bytecode only loads on 3.12).

```bat
setup.bat      :: creates .venv and installs requirements.txt
build.bat      :: -> dist\HOK ACE Mobile English Patcher.exe
run.bat        :: run from source without building
```

If `py -3.12` is not available: `set PYTHON=C:\path\to\python3.12.exe` before `setup.bat`.

`build\` (PyInstaller scratch), `dist\` and `.venv\` are generated and can be deleted anytime.

## What the patcher does on the phone

1. Pulls the installed APK, names the app in its manifest, re-signs it with the project key, and builds
   a temporary `android:debuggable` copy for data access via `run-as`.
2. Reads the language packages from the game data, builds the translated packages in the chosen language
   (`tools/build_device_patch.py`), pushes them back and verifies them.
3. Reinstalls the normal re-signed APK.

The debuggable copy must never be left installed: the game dies a few seconds into Unity startup
under it (measured on device, signal 7, bus error), so an interrupted run looks like a broken patch.
`patcher_core` recognises its own access APK and refuses to cache it as the game APK, which is how a
run that dies between steps 1 and 3 recovers.

That re-signed APK is the game's own file with one entry rewritten, `AndroidManifest.xml`, which is
where the debug flag and the app's name live. The name is `Honor of Kings: ACE` (`APP_NAME` in
`app/patcher_core.py`), written by `tools/axml_label.py` into the `<application>` label and into every
component that carries the same label reference: the launcher entry has no label of its own and
inherits that one, and the task switcher reads the activity's. It is a literal in the manifest, so the
game's own `R.string.game_name` and anything reading it are untouched. Renaming is cosmetic, so a
manifest it cannot read leaves the name as it is and the run continues, with a log line saying so.

The game's data has two layers, and the patcher writes to the second one:

| layer | where | contents |
|---|---|---|
| **prime**, built into the APK | `assets/bin/Data/Package/builtin/<id>/` | every asset as the APK was built |
| **override**, downloaded | `files/QtsVFSCache/packages/<id>/` | only the assets that changed since that build |

The game reads override first and falls back to prime, so an asset that exists only in prime is
unreachable by an in-place edit. The pulled APK is therefore a patch input, not just something to
re-sign, and there are two ways to carry that content into the override copy:

- **Append the asset to the package that is already there** — what a normal run does (`qts_insert.py`,
  run by `package_rebuild.add_prime_only`). The asset's index record and its chunk slot are taken from the
  APK's own prime copy of the package, which already carries the asset, so every key the game derives comes
  with them; the payload is re-encoded and both are appended to the target's shard and index and linked
  into their B-trees. Nothing else in the container moves, so the package keeps the shape the game
  already reads, and no builder is involved. This is how packages `1`, `1050016095` and `21` get the
  content they keep only in the APK: `1`'s 297 prime-only tables, `1050016095`'s 71 prime-only textures,
  and `21`'s Central Plains panel.
- **Lay the package out again** with Tencent's own builder (`resources/qtsvfs/`), per package named in
  `package_rebuild.REBUILD_PACKAGES` — **empty**, because the append reaches everything the catalog
  covers while leaving the container's shape alone. The rebuild is kept as the path for a package that has
  to be re-laid out rather than added to, and it is the pipeline's only caller of `QtsVFS.dll`. It
  recompresses the whole *override* copy, so what it costs is that copy's size, not the APK's — package
  `21` would cost about 40 MB to lay out rather than the 511 MB its APK copy suggests.

The patcher's own working data (~8 GB: pulled APK, packages, sessions) goes to the folder chosen in the app
(default `HOK ACE Patcher Data` next to the exe), not into this project.

## Translation coverage

The pipeline translates **text tables and textures**. Text is staged in `full` mode and falls back to
`fit-only` when replacements compete for slack, dropping the tables that will not fit; a table the stager
cannot fit is then appended to the end of the shard rather than lost. It stages **the catalog's tables and
nothing else**: the scanner can recognize and resolve a localization table the catalog has no record for,
and such a table is left Chinese, because translating anything outside the catalog needs a device cycle
(see the `extra_text` allowlist below). Textures are a second pass that ports each reviewed edit in
`resources/catalog/` onto the device's ASTC textures, which the game stores Oodle-compressed; the changed
chunks are appended to the package shard and repointed in its B-tree, so every asset keeps its chunk count.
An atlas the catalog edits sprite by sprite (`regions`) is placed by the device's own sprite table rather
than at the catalog's PC offsets, because the mobile build packs the Career atlas differently: the offset
port used to write nine of its English labels onto other sprites. That atlas also carries two labels this
repo draws itself (MY SKINS, TOTAL PROFIT) and has the sprites the old port damaged redrawn.

The Talent Card name dictionary keeps its original 307,200-byte chunk size and gains one chunk
using a native lookup key measured offline and verified on the phone. This fixes grid labels
such as `Arena Tiger` that previously displayed raw `#BE08...` refs. A normal patch run needs no
builder DLL for this fix. Rerunning the updated patcher also repairs an older patched copy, even
when its dictionary strings are already English.

A third pass, `extra_text`, translates display strings the catalog has no table for. Most of them live in
config assets rather than localization tables, and its allowlist for those, `SAFE_ASSETS`, is **empty**:
every config asset ever cleared on a phone was withdrawn later, because translating one can take a screen
with it. Task names make a tournament replay force-close; the four chessplayer-skill assets remove the
skill-description button; mail, quiz and "not open yet" notices remove the game button after pressing start
and blank the encyclopedia; the rule pages remove the Announcement screen's back arrow and title; and the AI
nicknames, display-text table and post-match compliments make every match end in a
`/未翻译UI/QTSFailureTips` popup, the client's QTS-failure notice. The withdrawn hashes and the symptom each
one causes are recorded beside the allowlist in `tools/extra_text.py`; do not add to that set without a
device cycle. The same class of edit had already broken the login screen, the Card menu and every prefab
label tried. What the pass still does is `SCRIPT_LABELS`: one hard-coded label in a Lua UI script, the
Effect Card filter's `通用`, replaced with the catalog's `General` and appended to package `10`.

Of the catalog's 398 texture edits, 395 exist somewhere in the mobile build under their own hash — 323 in
the downloaded layer and 73 in the APK's built-in layer, one asset keyed in both — and the other three are
reached through the device revision of their card, so a run applies all **398**. `7B4CC5DF48336D2D`,
Central Plains' fourth wide faction panel, sits in the APK's package `21` and reaches the phone by append:
the panel is translated from its prime revision and one record is added to the override copy of `21`, which
therefore keeps the container shape the game already mounts. A *rebuild* of `21` also applies it — 4863
assets laid out, 48.7 MB, mounted by the game, the panel read back as English — but on the phone it costs a
card: the Factionless hero Yixing then draws as the game's grey placeholder, with art and faction bar
missing, while Tencent's own copy of the package draws that card correctly. Package `21` is therefore kept
out of `REBUILD_PACKAGES`.

Three edits, `197CC5393D16E3CB`, `884E0B4581F47CF7` and `89C771ECFCDC7FBE`, are in neither layer under
their own hash: they are effect-card faction bands, and the mobile build carries each card under another
hash. `mobile_graphics.DEVICE_REVISIONS` maps each edit to the one package-`15` card whose band matches its
group's band (mean difference 0.01-0.02; the next closest card is 0.38), which is how the Riverlands card
Armed Power reads *Riverlands* instead of `大河流域`.

A device chunk's framing is per chunk and self-describing: stored when its compressed and uncompressed
sizes agree, a Zstandard frame when the payload opens with that magic, otherwise whatever the entry's
compression id says — `1` and `9` LZ4, `4` Oodle. One asset can mix them, and package `21` has twelve
that do. `tools/qts_relocate.py` follows the payload rather than the id for that reason; a reader that
went by the id alone left 1285 of that package's 4866 entries unreadable, which is what a rebuild of `21`
needs and could not have. It is left out for the card above instead, so the translation of that one
texture stays reachable only by a rebuild that is worse than the Chinese ribbon it would fix.

A whole-image replacement can also land when the device revision of the same art is a different size
from the catalog's record — a build re-cutting a card by one block row changes the raw size, which by
itself would reject the edit. The texture pass then measures the alignment between the two images and
copies only the label across, leaving the rest of the device's own pixels alone; an image that does not
align is still skipped rather than rescaled. On the game data used to develop this, one replacement
(`C9E29F61B9E73713`, Three Kingdoms, 592x816 in the catalog and 592x824 on the device) is recovered this
way. Which screen draws that asset has not been established, so treat the recovery as a correctness fix
rather than a visible one.

The catalog keys 27 wide per-faction panels at 568x304 — four art variants per faction and three for
Mecha — and the Card Info view draws its faction ribbon from that family rather than from the card's own
art: the grid card `F72420296646DC5B` is in the catalog and on the device, and the pass rewrites its
ribbon, yet the Card Info view for that same card still shows `河洛`. So the faction ribbon is translated
wherever it is baked into the card art, and comes from the separate wide panel in the views that draw it
that way. It is art rather than text, so no text table can reach it: in that same Card Info view every
other string, including the faction name inside a card's rules text, is already English.

An earlier measurement concluded the panel family was absent from the build. That conclusion was drawn
against the **downloaded** layer only, and is superseded. `tools/research/ribbon_id_hunt.py` scores every
texture in that layer whose raw size could hold a 568x304 panel — each of the six ASTC footprints, and
every height inside the 16 px the label splice is able to absorb — against all 27 English payloads; the
test separates the family by an order of magnitude, a genuine sibling measuring between 0.05 and 2.5
depending on the footprint while an unrelated texture of the same shape measures about 14. Within that
layer its negative result held: the Sunset panel behind `BCCC8C957621FA27` matched its own payload at
1.1, and the best of the other 54 candidates scored 11.0, rendering as black frames, gradients, event
banners and buttons rather than panels.

Counting the APK's built-in layer as well changes the answer: 26 of the 27 panels are there under the
catalog's own ids — 25 of them in package `1050016095` and `7B4CC5DF48336D2D` in package `21` — and the
Sunset panel the hunt did find is in the downloaded layer. A run applies 26 of the 27: the 25 through the
rebuild of `1050016095`, the Sunset panel in place, and not `7B4CC5DF48336D2D`, whose package costs the
card listed in the coverage section. Which panel a card's Card Info view draws was settled on the device:
the revision the APK holds for `7B4CC5DF48336D2D` renders as `❖ 河洛 ❖` on the maroon bar, exactly the
ribbon a Central Plains card draws in that view, and a rebuild carrying the English payload of that same
panel was put on the phone, read back as `Central Plains`, and withdrawn again once the price showed up.

`tools/research/prime_probe.py` prints that census: what each package keeps only in the APK, and how much
of it the catalog covers. A search for a missing asset has to run over both layers, which is the lesson
the earlier measurement paid for.

The catalog's card coverage is also narrower than it looks. Package `15` holds 3990 textures, 1994 of
them card-shaped, and the catalog's 299 entries at that shape are the **hero** cards — the other **1695**
are Talent, skill and effect cards, whose bottom band carries a type word or a card name rather than a
faction, and which the catalog does not translate at all. Decoding two of them shows `技能` beside an
already-English `SKILL`, and a `TALENT` card whose band reads `钻石狂澜`. The English for those names is
in the catalog and in some cases already drawn in the art, so what is missing is the *rendering*: this is
the largest visible gap left, and closing it needs a pass that draws text in the band's own font, colour
and position, because there is no catalog payload to copy. Nothing here draws text yet.

Package `1` is where the two layers matter most for text. It holds 2492 of its 2873 assets only in the
APK, 408 of them catalog text tables, of which 298 translate — 51,095 records, the chessplayer names and
their skills, talents and secret skills among them. The append carries **297 of the 298** into the
downloaded copy of the package, which is the layer the game reads first; the one it leaves out,
`3A70308AAF6F18F8`, is a 60-byte table whose LZ4 block lands exactly on its own length, which this format
cannot tell apart from a *stored* chunk. The catalog tables the downloaded copy already holds are staged
in place or relocated, and four more assets are rewritten by the extra-text pass.

The stager needs room in the package's shard to replace a table with a longer one, and when the shard has
none the staging loop drops that table and restages with what is left — on this data it used to drop 11 of
package `1`'s 92, every one of them a chessplayer skill, talent or secret-skill table. The drop is now a
relocation instead: a table that will not fit its slot is appended to the end of the shard. Its
chunk count is preserved except for the measured Talent Card dictionary fix described above. Whatever still cannot be applied is reported rather than
looking like a clean run: `text_skipped` in `device_patch_summary.json`, a line in the run log, and the
count in the app's `translate` step and in its final message. An asset the append pass could not add is
reported the same way, in `append_skipped`, which counts the images and the tables separately so the app
can say what stays in Chinese and of which kind. On this data `text_skipped` and `graphics_skipped` are
empty, and `append_skipped` holds the one table above.

Resource tokens such as `{Energy}`, `{LordExp}` and `{LordHp}` are expanded to English terms
(`Energy`, `Chessplayer EXP`, `Chessplayer HP`) in the staged packages, so the client no longer
expands them to Chinese. A space is inserted wherever the term would otherwise run into a preceding
word or placeholder, or into a following word or signed value. Beyond that the pipeline deliberately
does not extend:

- Extra text tables outside the staged packages are not translated, and no texture outside
  `resources/catalog/` is, apart from the two Career-atlas labels in `resources/sprites/`.

Two allowlists decide how far the display strings the catalog has no table for are taken. `SAFE_ASSETS`
in `tools/extra_text.py` holds the config assets a device cycle has cleared (none today); `CANDIDATE_ASSETS` beside it
holds the fifteen the asset note names as *not tried*, each resolved to the hash the package carries and
measured — `tools/research/extra_text_candidates.py` prints that table, and checks that a run naming no
candidate plans the allowlist and nothing else. Four of the fifteen are display-label tables the catalog
covers: `63922EF4D4C86526` is `幻化`/`夺宝`/`限时`, `7E3F57D727FA8625` is `道具`, `3914DBBFECD1E54D` is
`高光表情`, and `4CEF98BEC79CB48C` is four more. The other eleven are guide-step, buff, nickname and
damage identifiers the catalog reaches at most 9% of, so the labels are the cycles worth running. A cycle
is one variable: `--cycle-asset <hash>` on the offline CLI enables exactly that asset for one run, the run
names it in `device_patch_summary.json`'s `cycle_assets`, and the hash joins `SAFE_ASSETS` only once a
phone has shown the screen it feeds. `docs/features/extra-text-cycles.md` holds the loop.

Re-running the patcher is safe: `qts_relocate.install_btree_slot_map()` makes the scanner follow the
shard's B-tree, so a second run reads the live chunks instead of superseded copies of relocated ones,
the texture pass treats a texture that already matches its English payload as done, and the append pass
leaves a package alone once its staged copy already holds the asset — appending a record it already has
would index the same B-tree key twice. A run that reuses an output directory therefore reports fewer
packages than that directory holds: the copy the first run appended to is left as it is, because it is
where the earlier result lives.

## Languages

The catalog directory is the language: `resources/catalog/` is English and `resources/catalog_id/` is
Bahasa Indonesia (`tools/languages.py`). The offline pipeline and the headless check take a language the
same way the app does:

```bat
.venv\Scripts\python.exe tools\build_device_patch.py --runtime resources\runtime --game <game-dir> ^
    --catalog resources\catalog_id --work <work-dir> --output <out-dir> --apk <path>\installed.apk
dist\HOK ACE Mobile English Patcher.exe --selftest <game-dir> <out-dir> id
```

A language catalog ships only the textures it re-draws; every other texture is the English edit. Today
that is the lobby's START GAME label, drawn as MULAI GAME. To re-draw another label, put its render at
`resources/catalog_<lang>/previews/<HASH>.png`, add it to `LABELS` in
`tools/research/make_language_payloads.py`, and regenerate; `--check` fails when a shipped payload is
out of date:

```bat
.venv\Scripts\python.exe tools\research\make_language_payloads.py
.venv\Scripts\python.exe tools\research\make_language_payloads.py --check
```

Text the game already ships in English stays English in an Indonesian run unless the catalog carries an
`english_updates` row for it, and switching an already-patched phone to the other language needs the
game's data reset first, as for any newer translation build (*Known limits*).

## Checking doc references

`tools/research/check_references.py` proves every repo path the docs name still exists. It scans every
tracked Markdown file, the staging entry point, the research tools and the build scripts for backticked
paths and Markdown links, skips what git ignores, and fails on any mention of a name on its retired-names
list. Exit code 0 means clean; otherwise it prints one `file:line: reason` per failure:

```bat
.venv\Scripts\python.exe tools\research\check_references.py
```

`tools/research/check_staging_contract.py` proves the staging summary contract lives in
`build_patch`'s docstring in `tools/build_device_patch.py` and that `AGENTS.md` only points to it. It
reads the docstring with `ast`, so it needs no runtime, and prints one line per failure; exit code 0
means the contract is in place:

```bat
.venv\Scripts\python.exe tools\research\check_staging_contract.py
```

## Checking the texture pass

`tools/research/check_graphics.py` needs neither a phone nor a game dump. It decodes every shipped
payload and compares it to its review render, round-trips the ASTC codec, asserts that a byte patch
changes nothing outside its patch ranges, builds a synthetic device revision to exercise the
label splice, and ports the Career atlas at a recorded device layout:

```bat
.venv\Scripts\python.exe tools\research\check_graphics.py
```

Add `--game <game-dir>` to repeat those assertions on the real textures read out of a game dump, and to
print the per-entry table of what the dump carries. By default that table lists only the entries the run
cannot translate — the ones that are absent from the build or were skipped — because the 320-odd applied
rows are not what needs looking at; `--table` prints all of them.

`tools/research/atlas_sprites.py table --package <game-dir>\WXQ_Data\Package\builtin\19` prints each
regioned atlas's catalog boxes beside the device's sprite rects; `restore` rebuilds the crops in
`resources/sprites/`, `labels --out <dir>` drafts labels without touching the shipped ones, and `--check`
verifies the shipped PNGs.

`tools/research/render_texture.py` renders one payload or device texture to PNG, for identifying a
texture by eye when the hash alone does not say what it is:

```bat
.venv\Scripts\python.exe tools\research\render_texture.py --hash C9E29F61B9E73713 --out <dir>
.venv\Scripts\python.exe tools\research\render_texture.py --game <game-dir> --size 121952 --out <dir>
```

`tools/research/ribbon_id_hunt.py` is the record of the search for the mobile build's own ids for the
wide Card Info panels. `--floor-only` needs no dump: it reprints the family and measures what a genuine
sibling of it scores at each device footprint, which is the baseline the search is judged against. With
`--game` it censuses the dump and scores every 568x304-shaped texture in it against all 27 payloads,
near-misses included, so a weak match is visible as a weak match. Like every tool that takes a dump, its
census covers the downloaded layer only — read the coverage section above before drawing a conclusion
about the build from a negative here:

```bat
.venv\Scripts\python.exe tools\research\ribbon_id_hunt.py --floor-only
.venv\Scripts\python.exe tools\research\ribbon_id_hunt.py --game <game-dir> --render <dir>
```

`tools/research/browse_assets.py` browses the device's textures as images, for finding one by eye. It
caches an index of every asset (package, id, uncompressed size) on first run — about a minute, instant
after — and then renders a size family or a whole package into contact sheets. The catch it exists to
make explicit is that an ASTC texture's geometry is not stored anywhere: the byte count fixes only the
*block count*, so the same bytes can be a 568x304 texture at 8x8 or an 852x456 one at 12x12. `--diagnose`
measures how the device resolves that, and the answer is useful — of the 322 catalogued textures the
build carries, 311 are 4x4, 10 are 6x6 and one is 8x8 — so 4x4 is the default footprint. Pinning it
leaves little but the axis split, which `--guess` settles two ways: a geometry matching a catalogued
dimension is trusted outright, since the catalog knows the game's real texture sizes, and otherwise the
candidates are decoded and the most coherent one kept — a wrong grid breaks continuity at every block
edge, which the pixels themselves show. `--candidates <size>` renders one asset at every geometry that
size admits, and remains the authoritative check when a family looks wrong:

```bat
.venv\Scripts\python.exe tools\research\browse_assets.py --game <game-dir> --sizes --packages
.venv\Scripts\python.exe tools\research\browse_assets.py --game <game-dir> --candidates 227856 --out <dir>
.venv\Scripts\python.exe tools\research\browse_assets.py --game <game-dir> --package 19 --render ^
    --guess --out <dir>
```

`--manifest` writes a CSV inventory of the selection — one line per asset id, with the geometry it would
be rendered at and how that geometry was decided — and `--all --manifest` covers the whole build.
`--all --render` renders every texture in it into sheets captioned with the full 16-character id. On the
game data used to develop this that is 25,053 of the 83,131 assets drawn on 522 sheets: the other 56,707
are config blobs a few hundred bytes long, and 1,369 do not decompress. Two more crash the ASTC decoder
outright, which no in-process code can catch — `--trace` logs each id just before it is decoded so the
offender can be named, and `--skip <id>` with `--resume` carries on past it. Rendering everything takes a
few minutes and writes about 350 MB.

## Known limits

- Direct WeChat/QQ login does not work on a re-signed APK; use *Scan to login*.
- After a game update: clear the game's data, let it re-download to the login screen, then patch again.
  Patch with the APK the phone has now: the prime layer comes from the pulled APK, so a package that was
  rebuilt against an older build's built-in assets is rebuilt again against the current one. The pull is
  skipped when the cached copy's size already matches, and re-taken when it does not.
- A rebuilt package is larger than the one it replaces, because it carries the APK's translatable content
  as well: on this data package `1` goes from 29.3 MB to 30.6 MB and package `1050016095` from 0.3 MB to
  2.5 MB. Rebuilding recompresses the package, so it is done for the two packages that gain by it and no
  others, and a third was tried and withdrawn: package `21`, whose rebuild cost a Factionless card.
- Re-running over an **already patched** install translates no more text: the scanner only translates
  tables that still hold Chinese, and it reports nearly everything else as already English. To pick up
  a newer translation build, reset the game's data first (previous bullet) so the tables are Chinese
  again. Textures are not affected by that limit — the texture pass compares each device texture
  against its English payload, so a re-run picks up any texture the previous run did not write.
- Not reachable by any patch through the game data, each tried and failed on the phone: rewriting package
  `19`'s Unity prefab labels (the lobby hangs, and rewriting only the 15 prefabs that show faction names
  crashes at start with `stack corruption detected`), and the chessplayer definition `A8BC70BB87700709`
  field 37 (lobby loading stalls even when every reference in packages 1 and 14 is renamed with it).
- Two entries of package `1` sit in the downloaded index with no payload of their own — their bytes are
  the APK's — so the rebuild reads those from the APK. One further entry, `56077AC5D3F0B677`, arrives
  declaring 7,597,568 bytes while its chunk stream holds 8,519,168. The rebuild carries the stream whole
  and records the length it carries, so that entry's declared size differs from the device's by 921,600
  bytes even though the stream itself is byte-identical. Together with the 16-byte token derived from
  that length, it is the only entry whose rebuilt form differs from the device's copy in a value the game
  may read: every other entry keeps its bytes and its declared size, and the one field that differs
  elsewhere is the record's own offset, which necessarily moves when the index is re-laid-out. Only a
  device run settles whether the length matters.
- Code injection into the APK and a "prebaked" APK with translated assets were both tried and fail
  (anti-cheat kill / `IsPrebuild errorCode:151`).
