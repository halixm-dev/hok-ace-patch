# HOK ACE Mobile English Patcher

Windows app that installs the English or Indonesian translation into 王者万象棋
(`com.tencent.tmgp.osgame`) on an Android phone over USB, without root. Pick the language under
**LANGUAGE** in the app before starting; the choice is remembered. The translation is written into the game data
**after** the in-game update finishes, because Tencent's updater applies binary diffs that break
if the language packages were modified inside the APK.

## Build

Requires Python **3.12** (the runtime bytecode only loads on 3.12).

```bat
setup.bat      :: creates .venv and installs requirements.txt
build.bat      :: -> dist\HOK ACE Mobile English Patcher.exe
run.bat        :: run from source without building
```

If `py -3.12` is not available: `set PYTHON=C:\path\to\python3.12.exe` before `setup.bat`.

`build\` (PyInstaller scratch), `dist\` and `.venv\` are generated and can be deleted anytime.

## What the patcher does on the phone

1. Pulls the installed APK, names the app in its manifest, re-signs it with the project key, and builds
   a temporary `android:debuggable` copy for data access via `run-as`.
2. Reads the language packages from the game data, builds the translated packages in the chosen language
   (`tools/build_device_patch.py`), pushes them back and verifies them.
3. Reinstalls the normal re-signed APK.

The debuggable copy must never be left installed: the game dies a few seconds into Unity startup
under it (measured on device, signal 7, bus error), so an interrupted run looks like a broken patch.
`patcher_core` recognises its own access APK and refuses to cache it as the game APK, which is how a
run that dies between steps 1 and 3 recovers.

That re-signed APK is the game's own file with one entry rewritten, `AndroidManifest.xml`, which is
where the debug flag and the app's name live. The name is `Honor of Kings: ACE` (`APP_NAME` in
`app/patcher_core.py`), written by `tools/axml_label.py` into the `<application>` label and into every
component that carries the same label reference: the launcher entry has no label of its own and
inherits that one, and the task switcher reads the activity's. It is a literal in the manifest, so the
game's own `R.string.game_name` and anything reading it are untouched. Renaming is cosmetic, so a
manifest it cannot read leaves the name as it is and the run continues, with a log line saying so.

The game's data has two layers, and the patcher writes to the second one:

| layer | where | contents |
|---|---|---|
| **prime**, built into the APK | `assets/bin/Data/Package/builtin/<id>/` | every asset as the APK was built |
| **override**, downloaded | `files/QtsVFSCache/packages/<id>/` | only the assets that changed since that build |

The game reads override first and falls back to prime, so an asset that exists only in prime is
unreachable by an in-place edit. The pulled APK is therefore a patch input, not just something to
re-sign, and there are two ways to carry that content into the override copy:

- **Append the asset to the package that is already there** — what a normal run does (`qts_insert.py`,
  run by `package_rebuild.add_prime_only`). The asset's index record and its chunk slot are taken from the
  APK's own prime copy of the package, which already carries the asset, so every key the game derives comes
  with them; the payload is re-encoded and both are appended to the target's shard and index and linked
  into their B-trees. Nothing else in the container moves, so the package keeps the shape the game
  already reads, and no builder is involved. This is how packages `1`, `1050016095` and `21` get the
  content they keep only in the APK: `1`'s 297 prime-only tables, `1050016095`'s 71 prime-only textures,
  and `21`'s Central Plains panel.
- **Lay the package out again** with Tencent's own builder (`resources/qtsvfs/`), per package named in
  `package_rebuild.REBUILD_PACKAGES` — **empty**, because the append reaches everything the catalog
  covers while leaving the container's shape alone. The rebuild is kept as the path for a package that has
  to be re-laid out rather than added to, and it is the pipeline's only caller of `QtsVFS.dll`. It
  recompresses the whole *override* copy, so what it costs is that copy's size, not the APK's — package
  `21` would cost about 40 MB to lay out rather than the 511 MB its APK copy suggests.

The patcher's own working data (~8 GB: pulled APK, packages, sessions) goes to the folder chosen in the app
(default `HOK ACE Patcher Data` next to the exe), not into this project.

## Translation coverage

Coverage is the staged text tables, the catalog edits, the two Career-atlas labels this repo draws
(MY SKINS, TOTAL PROFIT) and one hard-coded Lua label — not a complete translation. Text is staged in
place, relocated when it will not fit, and appended from the APK's prime layer when the override layer
lacks it; the text pass stages the catalog's tables and nothing else. A run applies all **398** of the
catalog's texture edits, three of them through a measured device revision of their card. Config bins
outside the catalog stay Chinese: the `extra_text` allowlist is empty, and a bin joins it only after a
device cycle. Whatever a run could not apply is reported in `device_patch_summary.json`
(`text_skipped`, `graphics_skipped`, `append_skipped`) and counted in the app's final message. The running
counts, what each layer carries, and what is knowingly left Chinese are in the
[coverage ledger](docs/translation-progress.md).

## Languages

The catalog directory is the language: `resources/catalog/` is English and `resources/catalog_id/` is
Bahasa Indonesia (`tools/languages.py`). The offline pipeline and the headless check take a language the
same way the app does:

```bat
.venv\Scripts\python.exe tools\build_device_patch.py --runtime resources\runtime --game <game-dir> ^
    --catalog resources\catalog_id --work <work-dir> --output <out-dir> --apk <path>\installed.apk
dist\HOK ACE Mobile English Patcher.exe --selftest <game-dir> <out-dir> id
```

A language catalog ships only the textures it re-draws; every other texture is the English edit. Today
that is the lobby's START GAME label, drawn as MULAI GAME. To re-draw another label, put its render at
`resources/catalog_<lang>/previews/<HASH>.png`, add it to `LABELS` in
`tools/research/make_language_payloads.py`, and regenerate; `--check` fails when a shipped payload is
out of date:

```bat
.venv\Scripts\python.exe tools\research\make_language_payloads.py
.venv\Scripts\python.exe tools\research\make_language_payloads.py --check
```

Text the game already ships in English stays English in an Indonesian run unless the catalog carries an
`english_updates` row for it, and switching an already-patched phone to the other language needs the
game's data reset first, as for any newer translation build (*Known limits*).

## Checking doc references

`tools/research/check_references.py` proves every repo path the docs name still exists. It scans every
tracked Markdown file, the staging entry point, the research tools and the build scripts for backticked
paths and Markdown links, skips what git ignores, and fails on any mention of a name on its retired-names
list. Exit code 0 means clean; otherwise it prints one `file:line: reason` per failure:

```bat
.venv\Scripts\python.exe tools\research\check_references.py
```

`tools/research/check_staging_contract.py` proves the staging summary contract lives in
`build_patch`'s docstring in `tools/build_device_patch.py` and that `AGENTS.md` only points to it. It
reads the docstring with `ast`, so it needs no runtime, and prints one line per failure; exit code 0
means the contract is in place:

```bat
.venv\Scripts\python.exe tools\research\check_staging_contract.py
```

## Checking the texture pass

`tools/research/check_graphics.py` needs neither a phone nor a game dump. It decodes every shipped
payload and compares it to its review render, round-trips the ASTC codec, asserts that a byte patch
changes nothing outside its patch ranges, builds a synthetic device revision to exercise the
label splice, and ports the Career atlas at a recorded device layout:

```bat
.venv\Scripts\python.exe tools\research\check_graphics.py
```

Add `--game <game-dir>` to repeat those assertions on the real textures read out of a game dump, and to
print the per-entry table of what the dump carries. By default that table lists only the entries the run
cannot translate — the ones that are absent from the build or were skipped — because the 320-odd applied
rows are not what needs looking at; `--table` prints all of them.

`tools/research/atlas_sprites.py table --package <game-dir>\WXQ_Data\Package\builtin\19` prints each
regioned atlas's catalog boxes beside the device's sprite rects; `restore` rebuilds the crops in
`resources/sprites/`, `labels --out <dir>` drafts labels without touching the shipped ones, and `--check`
verifies the shipped PNGs.

`tools/research/render_texture.py` renders one payload or device texture to PNG, for identifying a
texture by eye when the hash alone does not say what it is:

```bat
.venv\Scripts\python.exe tools\research\render_texture.py --hash C9E29F61B9E73713 --out <dir>
.venv\Scripts\python.exe tools\research\render_texture.py --game <game-dir> --size 121952 --out <dir>
```

`tools/research/ribbon_id_hunt.py` is the record of the search for the mobile build's own ids for the
wide Card Info panels. `--floor-only` needs no dump: it reprints the family and measures what a genuine
sibling of it scores at each device footprint, which is the baseline the search is judged against. With
`--game` it censuses the dump and scores every 568x304-shaped texture in it against all 27 payloads,
near-misses included, so a weak match is visible as a weak match. Like every tool that takes a dump, its
census covers the override layer only — read the coverage ledger before drawing a conclusion
about the build from a negative here:

```bat
.venv\Scripts\python.exe tools\research\ribbon_id_hunt.py --floor-only
.venv\Scripts\python.exe tools\research\ribbon_id_hunt.py --game <game-dir> --render <dir>
```

`tools/research/browse_assets.py` browses the device's textures as images, for finding one by eye. It
caches an index of every asset (package, id, uncompressed size) on first run — about a minute, instant
after — and then renders a size family or a whole package into contact sheets. The catch it exists to
make explicit is that an ASTC texture's geometry is not stored anywhere: the byte count fixes only the
*block count*, so the same bytes can be a 568x304 texture at 8x8 or an 852x456 one at 12x12. `--diagnose`
measures how the device resolves that, and the answer is useful — of the 322 catalogued textures the
build carries, 311 are 4x4, 10 are 6x6 and one is 8x8 — so 4x4 is the default footprint. Pinning it
leaves little but the axis split, which `--guess` settles two ways: a geometry matching a catalogued
dimension is trusted outright, since the catalog knows the game's real texture sizes, and otherwise the
candidates are decoded and the most coherent one kept — a wrong grid breaks continuity at every block
edge, which the pixels themselves show. `--candidates <size>` renders one asset at every geometry that
size admits, and remains the authoritative check when a family looks wrong:

```bat
.venv\Scripts\python.exe tools\research\browse_assets.py --game <game-dir> --sizes --packages
.venv\Scripts\python.exe tools\research\browse_assets.py --game <game-dir> --candidates 227856 --out <dir>
.venv\Scripts\python.exe tools\research\browse_assets.py --game <game-dir> --package 19 --render ^
    --guess --out <dir>
```

`--manifest` writes a CSV inventory of the selection — one line per asset id, with the geometry it would
be rendered at and how that geometry was decided — and `--all --manifest` covers the whole build.
`--all --render` renders every texture in it into sheets captioned with the full 16-character id. On the
game data used to develop this that is 25,053 of the 83,131 assets drawn on 522 sheets: the other 56,707
are config blobs a few hundred bytes long, and 1,369 do not decompress. Two more crash the ASTC decoder
outright, which no in-process code can catch — `--trace` logs each id just before it is decoded so the
offender can be named, and `--skip <id>` with `--resume` carries on past it. Rendering everything takes a
few minutes and writes about 350 MB.

## Known limits

- Direct WeChat/QQ login does not work on a re-signed APK; use *Scan to login*.
- After a game update: clear the game's data, let it re-download to the login screen, then patch again.
  Patch with the APK the phone has now: the prime layer comes from the pulled APK, so a package that was
  rebuilt against an older build's prime assets is rebuilt again against the current one. The pull is
  skipped when the cached copy's size already matches, and re-taken when it does not.
- A rebuilt package is larger than the one it replaces, because it carries the APK's translatable content
  as well: on this data package `1` goes from 29.3 MB to 30.6 MB and package `1050016095` from 0.3 MB to
  2.5 MB. Rebuilding recompresses the package, so `REBUILD_PACKAGES` is empty and the append carries that
  content instead; package `21`'s rebuild was tried and withdrawn because it cost a Factionless card.
- Re-running over an **already patched** install translates no more text: the scanner only translates
  tables that still hold Chinese, and it reports nearly everything else as already English. To pick up
  a newer translation build, reset the game's data first (previous bullet) so the tables are Chinese
  again. Textures are not affected by that limit — the texture pass compares each device texture
  against its English payload, so a re-run picks up any texture the previous run did not write.
- Not reachable by any patch through the game data, each tried and failed on the phone: rewriting package
  `19`'s Unity prefab labels (the lobby hangs, and rewriting only the 15 prefabs that show faction names
  crashes at start with `stack corruption detected`), and the chessplayer definition `A8BC70BB87700709`
  field 37 (lobby loading stalls even when every reference in packages 1 and 14 is renamed with it).
- Two entries of package `1` sit in the override index with no payload of their own — their bytes are
  the APK's — so the rebuild reads those from the APK. One further entry, `56077AC5D3F0B677`, arrives
  declaring 7,597,568 bytes while its chunk stream holds 8,519,168. The rebuild carries the stream whole
  and records the length it carries, so that entry's declared size differs from the device's by 921,600
  bytes even though the stream itself is byte-identical. Together with the 16-byte token derived from
  that length, it is the only entry whose rebuilt form differs from the device's copy in a value the game
  may read: every other entry keeps its bytes and its declared size, and the one field that differs
  elsewhere is the record's own offset, which necessarily moves when the index is re-laid-out. Only a
  device run settles whether the length matters.
- Code injection into the APK and a "prebaked" APK with translated assets were both tried and fail
  (anti-cheat kill / `IsPrebuild errorCode:151`).
