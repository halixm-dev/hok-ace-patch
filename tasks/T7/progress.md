## Findings (file:line)

### Correctness / quality

1. **(non-critical) 319 of 3384 produced strings glue the English term to the following word.** `tools/resource_tokens.py:39-45` inserts a space only when the token is *preceded* by a digit or `}` (line 43); a token followed by a letter is replaced bare (line 44). Real outputs: `Energyis available until -15`, `{Energy}Big Bang` → `EnergyBig Bang`, `3{Energy}Reward` → `3 EnergyReward`, `get5{Energy}，5{LordHp}and1Special Equipment plate.` → `5 Chessplayer HPand1Special Equipment plate.`, `Consume{0|3}{Energy}to Obtain` → `Consume{0|3} Energyto Obtain`, `Current{Energy}:` → `CurrentEnergy:`. English-only, but visibly run-on; before this change those same strings rendered `能量` (also bad, differently). The rule set is inherited verbatim from `hok-ace-mobile-en/tools/resource_tokens.py:34-38`, so this is not drift — but the spec (`docs/features/resource-token-expansion.md:73-77`) never analyses the following-word case and README:51-53 promises "card text reads fully English". A following-letter space rule would fix it and would need its own full re-verification run (it can only grow strings, so it interacts with slot slack).
2. **(non-critical) `{LordExp}-` → `Chessplayer EXP-`.** The normalisation at `tools/resource_tokens.py:45` only matches `EXP\+`; `{LordExp}-{3|2}` (44 occurrences pre-fix) renders `Chessplayer EXP-2`, inconsistent with the documented `Chessplayer EXP +{0}` phrasing the spec cites as the target at spec:71-77.
3. **(non-critical, latent) The `Chessplayer EXP+` normalisation is not gated on the token actually being present.** `tools/resource_tokens.py:45` runs over the whole string, so a field that carries some *other* `{Name}` token and the literal text `Chessplayer EXP+5` would also be rewritten. Verified synthetically (`expand_resource_tokens("Chessplayer EXP+5 and {Energy}")` → `"Chessplayer EXP +5 and Energy"`); 0 occurrences in the corpus, so no real effect. The early-return guard at line 39 (`"{" not in text`) does *not* prevent this — it only suppresses the normalisation for brace-free text, which is exactly the text the walker's predicate rejects anyway (`tools/resource_tokens.py:115`), so the guard is self-consistent and useful for direct callers.
4. **(non-critical) The spec's absolute error claim is stronger than the code.** `docs/features/resource-token-expansion.md:122` says "Token expansion never propagates an exception out of `build_patch`", but in `tools/build_device_patch.py:58` `path.read_bytes()` and in line 65 `path.write_bytes(expanded)` sit **outside** the `try`, so an `OSError` (read error, disk full, permission) propagates and aborts the device step. The write is also non-atomic (no temp-file + replace), so a failure mid-write can leave a truncated asset in the work dir; the exception then propagates, so the truncated file is never staged — no corrupt package can reach the phone, but the sentence should be narrowed to "a parse failure never propagates".
5. **(non-critical) Per-asset skip is silent outside the log, and the hook's return value is discarded.** `tools/build_device_patch.py:61-63` logs `token expand skipped <name>: <error>` and continues, per spec; `build_device_patch.py:86` throws away the returned count, so the `counts`/`packages` payload carries no evidence of a skip. A regression in which every asset failed to parse would show up only as a missing log line (the GUI summary would look normal). Zero skips in this run, so nothing to fix now — but the log is the only signal.
6. **(non-critical) An asset can be partially expanded.** `tools/resource_tokens.py:121-125` swallows a nested `NotMessage` per sub-message while the rest of the asset still gets written, so failure granularity is "field atomic, asset mostly rewritten". Measured: exactly one swallowed sub-message in the whole corpus — asset `EBB4B2DDCD3E736F.assets`, field path `[1,2]`, 1793 bytes (`Chromatic Fade robbed this World of color…`), **0 resource tokens** — and total changes stayed 3384 with byte-identical output, so nothing was actually missed. Same behaviour as the reference. Worth one sentence in the spec rather than a change.
7. **Checked and clean (recording these so they are not re-litigated):** `_varint` (`tools/resource_tokens.py:58-68`) is byte-identical to `hok-ace-mobile-en/tools/pb_text.py:20-30`, rejects >10-byte varints, and cannot loop forever (every branch advances `pos`); the `end > len(data)` checks at lines 111 and 130 cover wire 1/5 truncation; the length prefix is correctly re-encoded (line 127) and a parse-back round trip of a nested message reproduces the inner length; `_CONTROL` (line 19) is identical to `pb_text.py:13`; expansion before staging is the right side of the ordering constraint and both staging paths read the expanded directory (`build_device_patch.py:92-98` fit-only, `:129` copytree full). Slot-capacity interaction is handled by the existing drop-retry loops (`build_device_patch.py:133-145` full, `:153-163` fit-only) plus `capacity_report`; in this run the drop count was unchanged at 15 and mode stayed `full`, so growth from `Chessplayer HP` (+11 chars) did not push anything new over slack.
8. **Not verifiable from outside the game:** whether any *live* (as opposed to superseded) string still renders with a Chinese expansion. The 207 residual raw token occurrences are in regions the fix never touched, and a byte-grep cannot decode the shard's string blobs (no zlib/gzip stream is present; the format transforms strings, which is why the handoff note warns against grepping the shards). An on-device check of Yixing / Niu Mo card info remains the only end-to-end proof, and no acceptance criterion required it.
